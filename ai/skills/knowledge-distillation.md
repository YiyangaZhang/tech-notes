# 将领域知识整理成可验证的 Agent Skill

> 原稿最早可见 Git 记录：2026-10-25；原稿最近 Git 修改：2026-10-25。公开版整理：2026-11-17。以上 Git 日期用于追溯，不等同于实际首次写作日期。
> 本文为通用知识整理，历史产品能力及版本细节需结合当前文档复核。

## 1. 这个技巧在补什么问题

三个真实痛点：

- **FDE 理解业务**：FDE（Forward Deployed Engineer）的第一步是把客户业务吃透（见 [FDE 职责与交付边界](../engineering/fde-delivery-boundaries.md) §1：深入客户真实环境、用客户的流程与约束工作）。业务文档、领域规则、客户黑话如果只停留在"读过"，agent 无法在客户现场调用；蒸馏成 skill 后，agent 按需加载，业务知识变成可执行工具。
- **同事 agent 的能力不可复制**：一个调教好的写作 agent，它的偏好藏在它的记忆里，本人没有文档。人走了、换了模型，能力就没了。
- **笔记/书/视频"看过用不起来"**：摘要只是压缩，不是结构化复用——读完还是不知道"什么时候该用什么"。

## 2. 设计原理：为什么这样设计能起作用

四步，每步都对着 LLM 的一个具体行为特性：

1. **历史记忆是主矿，行为题是验证器**：目标 agent 若带长期记忆（反复调教过的写作 agent），它"一直怎么做"的回忆就是第一来源——直接让它调用历史偏好并引用原话/实例，规则标注【历史偏好/本次新想/推测】。LLM 没有可靠内省，所以自述必须过"来源充分性"（能对到成品才算数，成品才是裁判）；【行为】【对比】【反事实】题负责逼出它说不出来、但做得出来的那部分。对没有历史记忆的陌生模型，才退回"行为题优先"。
2. **三重验证＋通用性关**：来源充分性（【历史偏好】且能对到成品／行为题＝过；【本次新想】【推测】必须找到一条成品证据才能晋级）、可执行性（能写成"触发→动作"的一条规则）、任务增益（删掉它生成质量会变差）。过三关后把规则里的书名/角色名换成占位符：仍成立→进通用 skill；只绑定某一本书→降级为"案例"单独立档。落选的留痕到 `rejected.md`，防止重复提炼。
3. **结构而非摘要＋按需分册**：SKILL.md 只当路由（≤4K 字），正文拆分册、用到才加载（token 按问题计费）；高频规则放前 500 字（上下文压缩从尾部截断，重要规则不能被截掉）。
4. **压力测试＋诱饵题**：每条 skill 用"看起来像、实际不是"的题考它，防规则误用（如 humanize 会把"他攥紧了拳头，眼眶发红"这种靠动作的人味写法误杀成"AI 味"）。

## 3. 如果未来模型变强，这个方法还有价值吗

- **会衰减的部分**：模型内省能力变强→自述题的权重可以上调；模型本身更会写小说→humanize 的部分规则内建，可删。
- **不过时的部分**：溯源（规则出自哪份成品）、可执行化（触发→动作）、压力测试、版本化 zip 交付、增量更新——这些是工程与协作常识，与模型强弱无关。

## 4. 和其他方案的比较

| 方案 | 做法 | 缺陷 | 我们取什么 |
|---|---|---|---|
| 抄 prompt | 把同事的提示词搬过来 | 只搬了输入，没搬决策规则 | 输入层 |
| 笔记式总结 | 写一篇"他擅长什么" | 不可执行 | 只当 AGENT_OVERVIEW |
| book-to-skill | 结构而非摘要＋分册＋高频前置 | 面向书，不面向人/agent | 分册、前置、深度预算 |
| cangjie RIA-TV++ | 五路提取＋三重验证＋压力测试＋双模式编译 | 不出题，只管提炼 | 验证、测试、编译 |
| nuwa-skill | 蒸馏人的表达 DNA | 输入是"人"，本项目是 agent | 输入替换为"成品集＋答题集" |
| **本方法** | 出题采集 → 五路提取 → 三重验证 → RIA++ 六段卡 → 分册 → 压力测试 → zip 交付 | — | 组合以上 |

## 5. 如何使用

下面是可复用的五步流程；项目专用任务书和输入包不随本文发布：

1. **出题采集**：任务书 93 题（82 基础题＋K 组 6 题＋5 复检题，含 1 道通用性迁移检验）投喂给目标 agent，同时附它自己的代表作当"偏好锚点"。**投喂时明确要求它优先调用历史记忆作答、每条规则标注【历史偏好/本次新想/推测】。**蒸馏目标是跨题材的通用作者判断，代表作只是采样材料。
2. **回收清洗**：删提示词残渣、礼貌用语、自问自答的元叙述。
3. **提取验证**：五路提取（框架/原则/案例/反例/术语）→ 三重验证，落选留 `rejected.md`。
4. **建卡分册**：RIA++ 六段卡（R 引用/I 解读/A1 关联/A2 应用/E 执行/B 边界）→ `SKILL.md` 路由＋分册＋`cheatsheet.md`＋`anti-patterns.md`＋`examples.md`＋`glossary.md`。
5. **测试打包**：压力测试（正常题/诱饵题/跨 skill 混淆）→ 打包 zip（含 `MANIFEST.json`、文件 sha256、验证状态）。

## 6. 适用场景 / 不适用场景

- ✅ 适用：方法论密集、决策规则多、可验证可溯源的领域（业务知识、写作偏好、工作流）。
- ❌ 不适用：纯即兴风格且无样本可采、一次性任务、规则无法写成"触发→动作"的内容。

> 验证边界：方法论的具体效果仍需用独立样本、成品比对和压力测试验证。

## 8. 方法局限与更优替代（诚实评估）

**这套方法的真实定位**：skill 化是"让 AI 复用规则"的工程手段，与"抽取"是两个层面——GitHub 生态（Anthropic skills、book-to-skill、cangjie/nuwa）提供了可供比较和实践的实现路线。配置克隆只在对方有 skill/配置时可用（对方纯用 AI 时拿不到任何东西）；评测集本质是"更多的验证"，与本题的"行为题＋成品比对＋压力测试"是同一范式的加深，不构成替代。

**三条局限（不因执行改善而消失）**：
1. 访谈只能抽出"说得出来"的规则；文风、品味、临场直觉是隐性知识，规则化会丢失——这对所有方法成立，包括微调（微调只是逼近行为分布，不是复制判断）。
2. 规则是对"当前模型弱点"的补丁（上下文截断→前置高频、长上下文稀释→分册）。模型变强后一部分 skill 会过期，需要定期做"过期审计"。
3. 规则库需要持续维护（版本、冲突消解、盲测），本身有成本；不维护会退化成噪音。

**不过时的价值（蒸馏的真正目标）**：
- 可审计、可版本化、可分享的**组织知识**；
- 尤其是"**模型做不到、必须人来拍板**"的判断点——模型再强，审美取舍、商业风险、客户边界这些需要人负责的决策不会消失。**蒸馏的第一优先级就是把这些"人介入点"显性化，再用它们指导其他 agent。**

**现实排序（按可落地性，不是按保真度）**：
1. 蒸馏成 skill（可落地、社区标准、可审计）← 本方案
2. 评测集加深验证（与 1 同一范式，做厚不做换）
3. 配置克隆（可遇不可求：对方有 skill/配置才行）
4. 微调/ML 蒸馏（需要数据量与训练，有规模才做）
